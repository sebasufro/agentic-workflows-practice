# `scan_gh_aw.py`

Script para descubrir repositorios que usan **GitHub Agentic Workflows** (`gh-aw`),
emparejar sus archivos fuente `.md` con los pipelines compilados `.lock.yml` y
generar un reporte Markdown con las últimas ejecuciones de GitHub Actions.

## Requisitos

- Python 3.10+
- `PyYAML` (opcional, pero recomendado para leer el frontmatter de los `.md`):

  ```bash
  python -m pip install pyyaml
  ```

- Un token de GitHub para la búsqueda de código. El script lo lee, en este orden:
  1. `--token`
  2. `--env-file` (o la variable `GH_AW_ENV_FILE`), si se indica
  3. el archivo `.env` del directorio actual o de la raíz del repositorio
  4. `GITHUB_TOKEN` o `GH_TOKEN` exportados en el entorno

  El `.env` debe tener una línea como:

  ```dotenv
  GITHUB_TOKEN=ghp_...
  ```

  Para repositorios públicos, un token clásico sin scopes o un fine-grained token
  sin permisos adicionales alcanza. Para repos privados, el token necesita
  `contents:read` y `actions:read`. El `.env` local tiene prioridad sobre las
  variables exportadas en el shell; para forzar el token del entorno usá
  `--token "$GITHUB_TOKEN"`. También se puede indicar otro archivo (la opción va
  antes del subcomando):

  ```bash
  python scripts/scan_gh_aw.py --env-file /ruta/a/.env discover --out repos.json
  ```

## Uso

### 1. Descubrir repositorios

Con la Code Search API de GitHub (requiere token):

```bash
python scripts/scan_gh_aw.py discover --out repos.json
```

La consulta por defecto es `gh-aw-metadata path:.github/workflows`. El marcador
`gh-aw-metadata` es la primera línea que `gh aw compile` escribe en cada
`.lock.yml`, por lo que identifica el uso real de la herramienta y no solo
menciones en documentación.

Para incluir archivos generados por versiones antiguas que no tenían esa línea:

```bash
python scripts/scan_gh_aw.py discover \
  --query 'generated by gh-aw path:.github/workflows' \
  --out repos.json
```

Sin token, se puede usar el índice público de Sourcegraph:

```bash
python scripts/scan_gh_aw.py discover --source sourcegraph --out repos.json
```

Sourcegraph no indexa todo GitHub, pero no consume el rate limit de GitHub y
sirve para explorar más allá del tope de 1.000 resultados de Code Search.

### 2. Analizar un repositorio

```bash
python scripts/scan_gh_aw.py repo PowerShell/vscode-powershell --runs 100
```

Genera `reports/PowerShell__vscode-powershell.md`. Opciones útiles:

- `--runs N`: máximo de ejecuciones a listar (100 por defecto).
- `--all-runs`: incluye todos los workflows, no solo los `.lock.yml`.
- `--max-run-pages N`: páginas de 100 ejecuciones a recorrer cuando se filtran
  workflows agénticos (20 por defecto).
- `--json-out archivo.json`: guarda también los datos crudos.
- `--out-dir`: directorio de salida (`reports` por defecto).

### 3. Analizar un lote

Para analizar todos los repositorios descubiertos:

```bash
python scripts/scan_gh_aw.py batch \
  --repos-file repos.json \
  --runs 100 \
  --out-dir reports
```

Además de un reporte por repositorio, genera `reports/index.md` con el resumen
comparativo.

#### Escanear solo un subconjunto

Para no gastar el rate limit en los cientos de repositorios descubiertos, podés
elegir un grupo antes de ejecutar el lote. Primero conviene previsualizar la
selección con `--dry-run`, que no hace llamadas a la API:

```bash
# Repositorios exactos, sin necesidad de repos.json
python scripts/scan_gh_aw.py batch \
  --repo PowerShell/vscode-powershell \
  --repo dotnet/runtime \
  --runs 100 --out-dir reports

# Solo una organización o usuario
python scripts/scan_gh_aw.py batch \
  --repos-file repos.json --org PowerShell \
  --dry-run

# Filtros combinados: incluir, excluir y limitar
python scripts/scan_gh_aw.py batch \
  --repos-file repos.json \
  --org dotnet --exclude dotnet/runtime \
  --limit 5 --dry-run

# Elegir 10 repositorios al azar de forma reproducible
python scripts/scan_gh_aw.py batch \
  --repos-file repos.json --sample 10 --seed 42 --dry-run
```

Opciones de selección de `batch`:

- `--repo OWNER/REPO`: agrega un repositorio exacto (repetible).
- `--only OWNER/REPO`: conserva solo ese repositorio (repetible).
- `--exclude OWNER/REPO`: descarta ese repositorio (repetible).
- `--org OWNER`: conserva solo repositorios de esa organización o usuario.
- `--limit N`: procesa como máximo N repositorios después de filtrar.
- `--sample N`: elige N al azar; `--seed` hace el resultado reproducible.
- `--dry-run`: muestra la selección y termina sin llamar a la API.

`--repos-file` acepta el JSON de `discover`, un JSON con una lista de nombres o
un archivo de texto con una línea `owner/repo` por repositorio:

```text
# seleccionados.txt
PowerShell/vscode-powershell
dotnet/runtime
```

```bash
python scripts/scan_gh_aw.py batch \
  --repos-file seleccionados.txt \
  --runs 100 --out-dir reports
```

Cada repositorio consume aproximadamente 2 llamadas fijas (metadata y árbol),
1 por cada par `.md`/`.lock.yml` y 1 o más por página de ejecuciones. Para
ajustar el presupuesto también podés bajar `--runs` o `--max-run-pages`.

## Qué contiene el reporte

1. **Archivos agénticos**: tabla de pares `foo.md` ↔ `foo.lock.yml` con propósito,
   disparador (`on:`), engine y safe outputs declarados en el frontmatter.
2. **Resumen de ejecuciones**: runs, éxitos, fallos, tasa de éxito, duración
   mediana y última ejecución por workflow.
3. **Últimas N ejecuciones**: fecha, workflow, archivo `.lock.yml`, evento, rama,
   estado, duración, actor y enlace directo al run.

## Cómo funciona el emparejamiento

Para cada repositorio se pide una sola vez el árbol recursivo:

```http
GET /repos/{owner}/{repo}/git/trees/{default_branch}?recursive=1
```

De ahí se toman los archivos bajo `.github/workflows/` y se emparejan por nombre
base:

```text
.github/workflows/issue-triage.md
.github/workflows/issue-triage.lock.yml
```

Los `.md` sin `.lock.yml` se listan aparte; suelen ser imports (`shared/`),
sub-agentes o workflows que todavía no se compilaron.

## Cómo se obtienen las ejecuciones

```http
GET /repos/{owner}/{repo}/actions/runs?per_page=100&page=N
```

Se recorren las páginas hasta juntar `--runs` ejecuciones cuyo `path` termine en
`.lock.yml`. El objeto de cada ejecución ya incluye los campos necesarios
(`name`, `path`, `event`, `head_branch`, `status`, `conclusion`, `created_at`,
`run_started_at`, `updated_at`, `actor`, `html_url`), así que no hace falta una
petición extra por ejecución.

Para obtener el detalle de jobs, pasos y tiempos exactos:

```http
GET /repos/{owner}/{repo}/actions/runs/{run_id}/jobs?per_page=100
```

Eso implica una petición adicional por ejecución; para 100 runs son 100
peticiones. El script no lo hace por defecto para no agotar el límite de 5.000
peticiones/hora en lotes grandes.

## Límites y advertencias

- **Code Search** solo indexa la rama por defecto, archivos menores a 384 KB y
  devuelve hasta 1.000 resultados por consulta (10 páginas × 100). El script
  avisa cuando se alcanza ese tope. Para conjuntos grandes, divide por
  `org:`, `user:` o complementa con Sourcegraph/BigQuery.
- **Rate limits**: 10 peticiones/minuto para Code Search; 5.000 peticiones/hora
  para la API REST autenticada (60/hora sin token).
- **Retención**: GitHub conserva las ejecuciones de Actions ~90 días por
  defecto en repos públicos. La API no devuelve ejecuciones ya purgadas.
- **Duración**: se calcula como `run_started_at → updated_at`. Si un run esperó
  aprobación, ese tiempo puede incluirse; por eso el resumen usa la mediana.
- **`deployments`**: si se necesitan deployments de GitHub (no ejecuciones de
  Actions), la API es `/repos/{owner}/{repo}/deployments` y
  `/repos/{owner}/{repo}/deployments/{id}/statuses`. Para workflows agénticos,
  lo relevante normalmente son los *workflow runs*.

## Ideas para seguir estudiando

- Leer el frontmatter completo de los `.md` (triggers, tools, network,
  safe-outputs) y construir una matriz de patrones de uso.
- Descargar artefactos de los runs (`GET /actions/runs/{run_id}/artifacts`) para
  ver los reportes que genera el agente.
- Cruzar los safe outputs con issues/PRs/comentarios creados
  (`GET /repos/{owner}/{repo}/issues?creator=...`) para medir el impacto real.
- Comparar la versión del compilador y el `frontmatter_hash` del `.lock.yml`
  entre repositorios para estudiar adopción y evolución.
