# Scripts de `gh-aw`

Cinco scripts separados:

- [`repo_search_agentic.py`](repo_search_agentic.py): descubre repositorios que
  usan **GitHub Agentic Workflows** (`gh-aw`) y genera `repos.json`.
- [`repo_scan_actions.py`](repo_scan_actions.py): analiza uno o varios
  repositorios, empareja sus archivos `.md` con los `.lock.yml` y genera
  reportes Markdown con las últimas ejecuciones de GitHub Actions.
- [`repo_fetch_issues.py`](repo_fetch_issues.py): exporta todos los issues de
  los repositorios de `repos.json` a un CSV, con el estado y el link directo a
  cada issue. Con `--with-details` agrega también descripción y etiquetas.
- [`repo_filter_issues.py`](repo_filter_issues.py): filtra los CSV de issues
  anteriores para quedarse con los que están relacionados con `gh-aw`, usando
  título, descripción, etiquetas y referencias al pipeline de CI/CD.
- [`repo_analyze_issues.py`](repo_analyze_issues.py): enriquece los issues
  filtrados con datos de la API y los clasifica por origen (automático de
  `gh-aw` o humano), tipo de problema, causa probable y forma de resolución.

`repo_scan_actions.py`, `repo_fetch_issues.py`, `repo_filter_issues.py` y
`repo_analyze_issues.py` reutilizan el cliente de GitHub y la carga de tokens de
`repo_search_agentic.py`, por lo que los cinco archivos deben estar en el mismo
directorio.

## Requisitos

- Python 3.10+
- `PyYAML` (opcional, pero recomendado para leer el frontmatter de los `.md`):

  ```bash
  python -m pip install pyyaml
  ```

- Un token de GitHub para la búsqueda de código. `repo_search_agentic.py` lo
  necesita para la Code Search API; `repo_scan_actions.py`, `repo_fetch_issues.py`
  y `repo_analyze_issues.py` lo usan para consultar repositorios, Actions e
  issues con un límite mayor. `repo_filter_issues.py` solo lo necesita con
  `--fetch-details`, para completar descripciones y etiquetas que falten en los
  CSV antiguos. Los scripts lo leen, en este orden:
  1. `--token`
  2. `--env-file` (o la variable `GH_AW_ENV_FILE`), si se indica
  3. el archivo `.env` del directorio actual o de la raíz del repositorio
  4. `GITHUB_TOKEN` o `GH_TOKEN` exportados en el entorno

  El `.env` debe tener una línea como:

  ```dotenv
  GITHUB_TOKEN=ghp_...
  ```

  Para repositorios públicos, un token clásico sin scopes o un fine-grained token
  sin permisos adicionales alcanza. Para repos privados, el token necesita
  `contents:read`, `actions:read` e `issues:read`. El `.env` local tiene
  prioridad sobre las variables exportadas en el shell; para forzar el token del
  entorno usá `--token "$GITHUB_TOKEN"`. También se puede indicar otro archivo
  (la opción va antes del subcomando):

  ```bash
  python scripts/repo_search_agentic.py --env-file /ruta/a/.env discover --out repos.json
  ```

## Uso

### 1. Descubrir repositorios

Con la Code Search API de GitHub (requiere token):

```bash
python scripts/repo_search_agentic.py discover --out repos.json
```

La consulta por defecto es `gh-aw-metadata path:.github/workflows`. El marcador
`gh-aw-metadata` es la primera línea que `gh aw compile` escribe en cada
`.lock.yml`, por lo que identifica el uso real de la herramienta y no solo
menciones en documentación.

Para incluir archivos generados por versiones antiguas que no tenían esa línea:

```bash
python scripts/repo_search_agentic.py discover \
  --query 'generated by gh-aw path:.github/workflows' \
  --out repos.json
```

Sin token, se puede usar el índice público de Sourcegraph:

```bash
python scripts/repo_search_agentic.py discover --source sourcegraph --out repos.json
```

Sourcegraph no indexa todo GitHub, pero no consume el rate limit de GitHub y
sirve para explorar más allá del tope de 1.000 resultados de Code Search.

### 2. Analizar un repositorio

```bash
python scripts/repo_scan_actions.py repo PowerShell/vscode-powershell --runs 100
```

Genera `reports/PowerShell__vscode-powershell.md`. Opciones útiles:

- `--runs N`: máximo de ejecuciones a listar (100 por defecto).
- `--all-runs`: incluye todos los workflows, no solo los `.lock.yml`.
- `--max-run-pages N`: páginas de 100 ejecuciones a recorrer cuando se filtran
  workflows agénticos (20 por defecto).
- `--json-out archivo.json`: guarda también los datos crudos.
- `--out-dir`: directorio de salida (`reports` por defecto).

### 3. Analizar un lote

Para analizar todos los repositorios descubiertos:

```bash
python scripts/repo_scan_actions.py batch \
  --repos-file repos.json \
  --runs 100 \
  --out-dir reports
```

Además de un reporte por repositorio, genera `reports/index.md` con el resumen
comparativo.

#### Escanear solo un subconjunto

Para no gastar el rate limit en los cientos de repositorios descubiertos, podés
elegir un grupo antes de ejecutar el lote. Primero conviene previsualizar la
selección con `--dry-run`, que no hace llamadas a la API:

```bash
# Repositorios exactos, sin necesidad de repos.json
python scripts/repo_scan_actions.py batch \
  --repo PowerShell/vscode-powershell \
  --repo dotnet/runtime \
  --runs 100 --out-dir reports

# Solo una organización o usuario
python scripts/repo_scan_actions.py batch \
  --repos-file repos.json --org PowerShell \
  --dry-run

# Filtros combinados: incluir, excluir y limitar
python scripts/repo_scan_actions.py batch \
  --repos-file repos.json \
  --org dotnet --exclude dotnet/runtime \
  --limit 5 --dry-run

# Elegir 10 repositorios al azar de forma reproducible
python scripts/repo_scan_actions.py batch \
  --repos-file repos.json --sample 10 --seed 42 --dry-run
```

Opciones de selección de `batch`:

- `--repo OWNER/REPO`: agrega un repositorio exacto (repetible).
- `--only OWNER/REPO`: conserva solo ese repositorio (repetible).
- `--exclude OWNER/REPO`: descarta ese repositorio (repetible).
- `--org OWNER`: conserva solo repositorios de esa organización o usuario.
- `--limit N`: procesa como máximo N repositorios después de filtrar.
- `--sample N`: elige N al azar; `--seed` hace el resultado reproducible.
- `--dry-run`: muestra la selección y termina sin llamar a la API.

`--repos-file` acepta el JSON de `discover`, un JSON con una lista de nombres o
un archivo de texto con una línea `owner/repo` por repositorio:

```text
# seleccionados.txt
PowerShell/vscode-powershell
dotnet/runtime
```

```bash
python scripts/repo_scan_actions.py batch \
  --repos-file seleccionados.txt \
  --runs 100 --out-dir reports
```

Cada repositorio consume aproximadamente 2 llamadas fijas (metadata y árbol),
1 por cada par `.md`/`.lock.yml` y 1 o más por página de ejecuciones. Para
ajustar el presupuesto también podés bajar `--runs` o `--max-run-pages`.

### 4. Exportar los issues a CSV

```bash
# Todos los repositorios de repos.json -> issues.csv
python scripts/repo_fetch_issues.py \
  --repos-file repos.json

# Un repositorio específico (no requiere repos.json)
# -> issues/vscode-powershell_issues.csv
python scripts/repo_fetch_issues.py \
  --repo PowerShell/vscode-powershell

# Un número fijo de repositorios de repos.json
# -> un CSV por repositorio dentro de issues/
python scripts/repo_fetch_issues.py \
  --repos-file repos.json --limit 10

# N repositorios al azar, de forma reproducible
# -> un CSV por repositorio dentro de issues/
python scripts/repo_fetch_issues.py \
  --repos-file repos.json --sample 10 --seed 42

# Filtrar por organización y excluir un repositorio
python scripts/repo_fetch_issues.py \
  --repos-file repos.json --org PowerShell \
  --exclude PowerShell/vscode-powershell

# Incluir descripción y etiquetas en el CSV (para el filtro)
python scripts/repo_fetch_issues.py \
  --repo PowerShell/vscode-powershell --with-details

# Forzar un único CSV aunque haya selección
python scripts/repo_fetch_issues.py \
  --repos-file repos.json --limit 10 \
  --combined --out issues-10.csv

# Forzar la separación aunque no haya filtros
python scripts/repo_fetch_issues.py \
  --repos-file repos.json --split

# Ver la selección y las rutas de salida sin llamar a la API
python scripts/repo_fetch_issues.py \
  --repos-file repos.json --org PowerShell --limit 5 --dry-run
```

`--repo` es repetible y puede combinarse con `--repos-file`; si se usa solo, no
carga `repos.json`. Sin `--repo` ni `--repos-file`, se lee `repos.json`.
`--only`, `--exclude`, `--org`, `--limit`, `--sample` y `--seed` funcionan igual
que en `repo_scan_actions.py batch`.

Cuando se seleccionan repositorios (`--repo`, `--only`, `--exclude`, `--org`,
`--limit`, `--sample` o un `--repos-file` distinto de `repos.json`), la salida es
un CSV por repositorio en `issues/`, con el nombre `{repo}_issues.csv`. Si dos
repositorios seleccionados comparten nombre, se usa
`{dueño}__{repo}_issues.csv` para evitar colisiones. Sin selección se genera un
único `issues.csv`; `--split` fuerza la separación y `--combined` fuerza un solo
archivo. En modo separado `--out` no se usa.

El script consulta `GET /repos/{owner}/{repo}/issues?state=all` para cada
repositorio, recorre todas las páginas y descarta los pull requests. Cada CSV
tiene estas columnas:

| Columna | Contenido |
|---|---|
| `nombre_repositorio` | Nombre del repositorio, sin el dueño |
| `dueño_repositorio` | Organización o usuario dueño del repositorio |
| `titulo` | Título del issue |
| `salida` | Estado actual del issue: `open` o `closed` |
| `link_issue` | URL pública directa al issue (`html_url`), no la URL de la API |

Con `--with-details` se agregan `descripcion` (cuerpo del issue) y `etiquetas`
(labels separadas por `;`) después de `titulo`. Esas columnas permiten que
`repo_filter_issues.py` busque en el cuerpo y en los labels sin volver a
consultar la API. Un CSV generado sin `--with-details` solo se puede filtrar por
título, salvo que se use `repo_filter_issues.py --fetch-details`.

Si un repositorio no tiene issues o los tiene deshabilitados, se informa durante
el progreso y el resto continúa. `--max-pages N` permite limitar las páginas de
100 issues por repositorio; `0` (por defecto) significa sin límite.

La paginación sigue los headers `Link` de GitHub. En repositorios con muchísimos
issues, GitHub usa paginación por cursor (`after`/`before`) y rechaza `page` a
partir de la página 100; el script detecta ese caso y continúa solo con el
cursor.

### 5. Filtrar issues relacionados con `gh-aw`

```bash
# Leer todos los CSV de issues/ y escribir filtered_issues/agentic_issues.csv
python scripts/repo_filter_issues.py

# Incluir también términos generales de CI/CD
python scripts/repo_filter_issues.py --include-pipeline

# Agregar palabras clave o etiquetas propias
python scripts/repo_filter_issues.py \
  --keyword "safe-outputs" --keyword "agentic" \
  --label "github-actions"

# Completar descripción y etiquetas consultando la API
python scripts/repo_filter_issues.py --fetch-details

# Leer un CSV concreto y escribir en otra ruta
python scripts/repo_filter_issues.py \
  --input issues/0gis0_issues.csv \
  --out issues/0gis0_agentic.csv
```

La salida por defecto es `filtered_issues/agentic_issues.csv`, en su propia
carpeta, para no mezclarla con los CSV originales de `issues/`. Se puede cambiar
con `--out`.

Si los CSV se generaron con `repo_fetch_issues.py --with-details`, el filtro
puede leer `descripcion` y `etiquetas` directamente y no necesita
`--fetch-details`.

El filtro busca, sin distinguir mayúsculas/minúsculas, en `titulo`,
`descripcion` y `etiquetas`. Por defecto reconoce señales como `gh-aw`,
`gh aw`, `agentic workflow`, `[aw]`, `.lock.yml` y `safe outputs`, además de
labels como `gh-aw`, `agentic` o `agentic-workflows`. Con `--include-pipeline`
suma `.github/workflows`, `github actions`, `workflow_dispatch`, `workflow run`,
`ci/cd` y `pipeline`.

El CSV de salida conserva las columnas de entrada y agrega `coincidencias`, que
indica qué palabra clave o etiqueta hizo coincidir cada issue. Si dos archivos
de entrada contienen el mismo `link_issue`, se conserva una sola fila.

### 6. Analizar los issues filtrados

```bash
# Analizar filtered_issues/agentic_issues.csv -> analysis/
python scripts/repo_analyze_issues.py

# Probar con los primeros 10 issues
python scripts/repo_analyze_issues.py --limit 10

# Incluir comentarios también en issues abiertos
python scripts/repo_analyze_issues.py --comments all

# Ignorar la caché y consultar todo de nuevo
python scripts/repo_analyze_issues.py --refresh

# Cambiar el directorio de salida y el paralelismo
python scripts/repo_analyze_issues.py \
  --out-dir analisis-2026-11 --workers 4
```

El script lee el CSV filtrado (por defecto
`filtered_issues/agentic_issues.csv`), consulta cada issue en la API y escribe
en `analysis/`:

| Archivo | Contenido |
|---|---|
| `issues_enriched.csv` | Un issue por fila, con origen, categoría, causa, evidencia y resolución |
| `summary.md` | Resumen general, tablas cruzadas, causas, ejemplos y comentarios de cierre |
| `por_categoria.csv` | Agregado por categoría de problema |
| `por_repositorio.csv` | Agregado por repositorio |
| `por_flujo.csv` | Agregado por workflow agéntico |

La caché de respuestas queda en `analysis/.cache/` (ignorada por git) para no
repetir llamadas al volver a ejecutar. `--refresh` la ignora; `--comments`
controla qué comentarios se consultan (`none`, `closed` o `all`).

El CSV enriquecido agrega estas columnas a las del filtro:

| Columna | Contenido |
|---|---|
| `numero_issue` | Número del issue en el repositorio |
| `estado` / `motivo_estado` | `open`/`closed` y `state_reason` de GitHub |
| `autor` / `tipo_autor` | Login y tipo (`User`, `Bot`, etc.) |
| `origen` | `automatico_gh_aw`, `humano`, `bot_otro` o `desconocido` |
| `flujo_trabajo` | Nombre del workflow agéntico extraído del cuerpo |
| `naturaleza` | `fallo_tecnico`, `limite_operativo`, `configuracion`, `bloqueo_seguridad`, `seguimiento`, `prueba`, `mejora` u `otro` |
| `categoria` | Categoría principal del problema |
| `categorias_secundarias` | Otras señales detectadas en el mismo issue |
| `causa_probable` | Explicación de la causa, con datos del cuerpo cuando están disponibles |
| `evidencia` | Fragmento textual que respalda la clasificación |
| `resolucion` | `abierto`, `cerrado_por_desarrollador`, `cerrado_por_autor`, `cerrado_automaticamente`, `descartado`, `duplicado` o `cerrado_sin_cerrador` |
| `cerrado_por` / `tipo_cerrador` | Quién cerró el issue y si es usuario o bot |
| `creado_en` / `cerrado_en` / `dias_abierto` | Fechas y duración |
| `expiracion` / `expirado` | Fecha `gh-aw-expires` del cuerpo y si ya venció |
| `comentarios` / `comentarios_humanos` | Cantidad total y de comentarios humanos |
| `etiquetas` | Labels separadas por `;` |
| `ultimo_comentario` / `autor_ultimo_comentario` | Último comentario humano (o el último disponible) y su autor |
| `coincidencias` | Motivo por el que el filtro incluyó el issue |

Categorías principales que reconoce:

- Fallos técnicos: `fallo_workflow`, `jobs_fallidos`, `fallo_engine`,
  `sin_safe_outputs`, `safe_output_fallido`, `datos_faltantes`,
  `herramientas_faltantes`, `resultado_incompleto`, `fallo_repo_memory`,
  `fallo_skill`, `lock_file_desactualizado`.
- Límites operativos: `presupuesto_ia`, `rate_limit`, `timeout_agente`.
- Configuración y seguridad: `fallo_modelo`, `fallo_secretos`,
  `archivos_protegidos`.
- Seguimiento: `seguimiento_no_op`, `seguimiento_deteccion`.
- Origen humano: `prueba_manual`, `solicitud_mejora`.

La clasificación es heurística: busca las señales que `gh-aw` escribe en el
cuerpo (`No Safe Outputs Generated`, `Missing Data Reported`,
`Lock File Out of Sync`, `Engine Failure`, etc.) y, si no encuentra ninguna,
usa el título y las etiquetas. La columna `evidencia` permite auditar cada
decisión; los casos con categoría `otro` conviene revisarlos a mano.

## Qué contiene el reporte

1. **Archivos agénticos**: tabla de pares `foo.md` ↔ `foo.lock.yml` con propósito,
   disparador (`on:`), engine y safe outputs declarados en el frontmatter.
2. **Resumen de ejecuciones**: runs, éxitos, fallos, tasa de éxito, duración
   mediana y última ejecución por workflow.
3. **Últimas N ejecuciones**: fecha, workflow, archivo `.lock.yml`, evento, rama,
   estado, duración, actor y enlace directo al run.

## Cómo funciona el emparejamiento

Para cada repositorio se pide una sola vez el árbol recursivo:

```http
GET /repos/{owner}/{repo}/git/trees/{default_branch}?recursive=1
```

De ahí se toman los archivos bajo `.github/workflows/` y se emparejan por nombre
base:

```text
.github/workflows/issue-triage.md
.github/workflows/issue-triage.lock.yml
```

Los `.md` sin `.lock.yml` se listan aparte; suelen ser imports (`shared/`),
sub-agentes o workflows que todavía no se compilaron.

## Cómo se obtienen las ejecuciones

```http
GET /repos/{owner}/{repo}/actions/runs?per_page=100&page=N
```

Se recorren las páginas hasta juntar `--runs` ejecuciones cuyo `path` termine en
`.lock.yml`. El objeto de cada ejecución ya incluye los campos necesarios
(`name`, `path`, `event`, `head_branch`, `status`, `conclusion`, `created_at`,
`run_started_at`, `updated_at`, `actor`, `html_url`), así que no hace falta una
petición extra por ejecución.

Para obtener el detalle de jobs, pasos y tiempos exactos:

```http
GET /repos/{owner}/{repo}/actions/runs/{run_id}/jobs?per_page=100
```

Eso implica una petición adicional por ejecución; para 100 runs son 100
peticiones. El script no lo hace por defecto para no agotar el límite de 5.000
peticiones/hora en lotes grandes.

## Límites y advertencias

- **Code Search** solo indexa la rama por defecto, archivos menores a 384 KB y
  devuelve hasta 1.000 resultados por consulta (10 páginas × 100). El script
  avisa cuando se alcanza ese tope. Para conjuntos grandes, divide por
  `org:`, `user:` o complementa con Sourcegraph/BigQuery.
- **Rate limits**: 10 peticiones/minuto para Code Search; 5.000 peticiones/hora
  para la API REST autenticada (60/hora sin token).
- **Retención**: GitHub conserva las ejecuciones de Actions ~90 días por
  defecto en repos públicos. La API no devuelve ejecuciones ya purgadas.
- **Duración**: se calcula como `run_started_at → updated_at`. Si un run esperó
  aprobación, ese tiempo puede incluirse; por eso el resumen usa la mediana.
- **`deployments`**: si se necesitan deployments de GitHub (no ejecuciones de
  Actions), la API es `/repos/{owner}/{repo}/deployments` y
  `/repos/{owner}/{repo}/deployments/{id}/statuses`. Para workflows agénticos,
  lo relevante normalmente son los *workflow runs*.

## Ideas para seguir estudiando

- Leer el frontmatter completo de los `.md` (triggers, tools, network,
  safe-outputs) y construir una matriz de patrones de uso.
- Descargar artefactos de los runs (`GET /actions/runs/{run_id}/artifacts`) para
  ver los reportes que genera el agente.
- Cruzar los safe outputs con issues/PRs/comentarios creados
  (`GET /repos/{owner}/{repo}/issues?creator=...`) para medir el impacto real.
- Comparar la versión del compilador y el `frontmatter_hash` del `.lock.yml`
  entre repositorios para estudiar adopción y evolución.
